# Архитектура и важные ограничения NewsHub

Этот документ фиксирует решения, которые необходимо учитывать при разработке,
деплое сайта и выпуске мобильных приложений.

Актуально на: 24 июля 2026 года.

## Текущая архитектура

```text
Браузер / iOS / Android
          |
          v
     newshub.kz
          |
        Nginx
          |
          +--> Node.js + Express SSR :3000
          |        |
          |        +--> Vue 3 + Vite
          |
          +--> api.newshub.kz
                   |
                   +--> Laravel + Octane :8002
                            |
                            +--> База данных
                            +--> Redis / Horizon / очереди
```

iOS- и Android-приложения сейчас являются тонкими нативными оболочками
Capacitor. В `capacitor.config.json` задано:

```json
{
  "server": {
    "url": "https://newshub.kz"
  }
}
```

Поэтому мобильные приложения загружают актуальный сайт с сервера, а не
встроенную копию Vue-фронтенда.

## Когда мобильные приложения пересобирать не нужно

Достаточно обновить сервер, если меняются:

- Vue-компоненты, страницы, стили и обычная логика интерфейса;
- SSR и Node.js-сервер;
- Laravel, бизнес-логика и фоновые задачи;
- контент;
- API при условии обратной совместимости со старыми версиями приложений.

После такого деплоя сайт, iOS и Android получают обновление с сервера.
Публиковать новые сборки в App Store и Google Play не требуется.

## Когда обязательна новая сборка iOS и Android

Нативные приложения необходимо пересобрать и выпустить заново, если меняются:

- Swift-, Objective-C-, Java- или Kotlin-код;
- состав или версия Capacitor-плагинов, если изменение затрагивает нативный код;
- разрешения в `Info.plist` или `AndroidManifest.xml`;
- push-уведомления, Firebase/FCM/APNs и их нативная конфигурация;
- иконка, splash screen, название приложения или bundle/application ID;
- deep links, universal links или app links;
- signing, entitlements, минимальная версия ОС или target SDK;
- `capacitor.config.json`, особенно `server.url`;
- фронтенд, который начинает вызывать нативный плагин, отсутствующий в уже
  опубликованной оболочке.

Нельзя считать, что пользователи сразу обновили приложение. Сервер и API
должны продолжать работать со старыми опубликованными версиями.

## Обратная совместимость API

- Не удалять endpoint, поле или старое поведение в том же релизе, где появился
  новый клиент.
- Сначала добавлять новый контракт и выпускать совместимые клиенты.
- Удалять старый контракт только после периода миграции и проверки доли старых
  версий.
- Новые поля ответа по возможности должны быть необязательными для клиента.
- Изменения авторизации, push-токенов и обязательных параметров считать
  потенциально несовместимыми.
- При несовместимом изменении использовать версионирование API.

## Зависимости и воспроизводимость сборок

- `composer.lock` и `package-lock.json` должны храниться в Git.
- На сервере использовать `composer install`, а не `composer update`.
- Для Node.js использовать `npm ci --legacy-peer-deps`, а не обычный
  `npm install`: плагин `@aashu-dubey/capacitor-statusbar-safe-area` версии
  2.1.2 объявляет peer dependency для Capacitor 5, тогда как проект использует
  Capacitor 6.
- Обновление зависимостей делать локально, проверять сборку и только затем
  отправлять изменённые lock-файлы.
- Основной Node.js runtime проекта — Node 20.
- Production сейчас работает на PHP 8.2 и Node 20; изменения должны оставаться
  совместимыми с этими версиями до запланированного обновления сервера.
- Проект использует Capacitor 6. Обновление major-версии требует отдельной
  проверки обеих нативных платформ.

## Правила безопасного деплоя

- Сначала собирать и проверять релиз вне production.
- Деплой фронтенда выполнять атомарно: HTML/SSR и статические файлы одного
  релиза должны переключаться вместе.
- Имена клиентских production-ассетов содержат content hash. Нельзя возвращать
  стабильные имена `[name].js` и `[name].css`: Safari и другие браузеры могут
  продолжать использовать файлы старого релиза.
- `sw.js`, `firebase-messaging-sw.js` и `manifest.webmanifest` должны
  отдаваться Nginx без долгого кеширования. Service worker не должен
  перехватывать навигационные HTML-запросы: новостной сайт всегда получает
  актуальный SSR-документ с сервера.
- Миграции базы данных сначала должны быть совместимы и со старым, и с новым
  кодом. Удаление колонок и другие необратимые изменения выполнять отдельным
  поздним релизом.
- Перед рискованными миграциями делать проверяемую резервную копию.
- После деплоя перезапускать или мягко перезагружать Node SSR, Octane и Horizon
  согласно процедуре деплоя.
- После переключения проверять как минимум сайт, API, авторизацию, SSR,
  очереди/Horizon и ключевые мобильные сценарии.
- Push в `main` автоматически запускает production-деплой через GitHub Actions.
  Workflow передаёт серверу точный SHA коммита, а сервер принимает только
  fast-forward до актуального `origin/main`.
- Автоматический деплой не запускает миграции базы данных. Совместимые миграции
  выполняются отдельным контролируемым шагом.
- Если production содержит tracked-изменения или уже выполняется другой деплой,
  автоматический деплой завершается без перезаписи файлов.
- Никогда не хранить пароли, SSH-ключи, токены или содержимое `.env` в Git и в
  этом документе.

## Если перейти на встроенный мобильный frontend

Если удалить `server.url` и начать поставлять `dist/mobile` внутри приложения,
каждое обновление Vue-фронтенда потребует новой сборки и публикации iOS и
Android. Такой переход нельзя делать случайно: он полностью меняет процесс
доставки обновлений.

## Известные ограничения и технический долг

- Для полноценной iOS-сборки с Firebase нужен настоящий
  `GoogleService-Info.plist` для bundle ID `kz.newshub.app`. В Xcode-проекте
  сейчас осталась локальная абсолютная ссылка на отсутствующий файл.
- Composer настроен решать зависимости как для production PHP 8.2.22, даже
  когда локальная машина работает на более новом PHP.
- Локальный Composer-аудит после точечного обновления всё ещё показывает три
  advisory для Laravel 10. Полное исправление требует Laravel 12.61.1 или новее,
  а значит — перехода с локальной Nova 4.24.2 на Nova 5 и проверки всех
  Nova-плагинов. Для загрузки Nova 5 необходимы данные действующей лицензии.
- По аудиту production от 23 июля 2026 года есть устаревшие системные пакеты и
  уязвимые Composer/npm-зависимости. Их следует обновлять отдельными
  контролируемыми релизами с регрессионной проверкой, а не командой обновления
  непосредственно на production.
